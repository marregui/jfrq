Three new questions for a recording (`hot`, `procs`, `waits`), a name for the thread that ran
while a lock had no recorded holder in `stalls`, and `jfrq-live watch`, which follows a running
JVM for hours by itself and ends with a summary.

## Assets

| File | Contents |
|---|---|
| `jfrq-0.2.0.zip` | `bin/jfrq` and `bin/jfrq-live` (with `.bat` for Windows), `lib/` with the three jars. No third-party dependencies. |
| `netty-demo-0.2.0.zip` | The Netty service the [tutorial](https://github.com/marregui/jfrq/blob/v0.2.0/docs/TUTORIAL.md) records; it injects event-loop faults on request. Not needed to analyse your own recordings. |
| `SHA256SUMS` | The SHA-256 of each zip. |

Each zip has a build provenance attestation:
`gh attestation verify jfrq-0.2.0.zip --repo marregui/jfrq`.

## Requirements

- JDK 25 to run. The launchers use `JAVA_HOME` when it is set, otherwise the `java` on the `PATH`.
- Recordings from any JDK 17 or later.

## Install

```
unzip jfrq-0.2.0.zip
export PATH="$PWD/jfrq-0.2.0/bin:$PATH"
jfrq --version
```

## New

| Command | Question it answers |
|---|---|
| `jfrq hot` | Where the CPU went: by thread family, by site (the innermost frame outside the JDK, or under `--app`), by what each site called below it, by leaf method, and over time. `--sites N` sets how many sites are split. |
| `jfrq procs` | Which processes the JVM started, how many a minute, from which threads and from which of your methods. On a 30-minute desktop recording: 464 starts, 421 of them `git`. |
| `jfrq waits` | What threads waited on in `Object.wait` and `park`, for how long and from which code, filtered by thread and by monitor class, `--sites N` sites per class as in `hot`. On one recording, the Swing event thread spent 25.3 s in 1,137 waits on the Java2D queue flusher, 19.0 s of it under one border painter. |
| `jfrq-live <pid> watch` | One process for `--for`: a `delta` window every `--every` with each `--ask` question answered on it, a row of CPU, heap, threads and open files in `samples.tsv` every `--sample`, a class histogram per window with `--histo`, and a summary table at the end. It exits 0 when the time is up or the JVM exits; 1 when a window failed, the recording was stopped, the JVM stopped answering, or the summary files could not be written; 130 or 143 when stopped by Ctrl-C or SIGTERM. On a desktop application for 6 minutes it cost 0.63 % of one core. |
| `jfrq-live <pid> histo`, `jfrq-live growth` | A class histogram from a running JVM, and the classes that grew at every step across two or more histograms, with a second table for those whose bytes grew while their instance count did not (larger arrays rather than more objects). Histograms saved with Windows line ends are read as they are. |

## Changed

- `stalls`: a park on a lock, or a monitor enter whose holder the recording does not name,
  now lists up to three other threads the sampler saw running during it, labelled a
  correlation, not a holder. Threads idle in native code (`accept`, `poll`, process waits)
  are left out. The JSON has `holder` and `meanwhile[]` on each stall.
- `alloc`: a virtual-thread sample heavier than every counter's growth is the carrier's
  history; it is left out and counted in the warning.
- `alloc`: a row whose bytes came partly from samples taken on virtual threads says what
  share (`16 samples (all virtual)`, `482 samples (95% virtual)`; `virtualBytes` in the JSON).
  Those samples are weighed by their carrier's allocation, so that part of the row can be
  far from its own code's: on a 29-minute recording, a method that allocates about 1 KB per
  call was ranked second at 203 MB, all of it on virtual threads.
- `alloc`: an allocation with no thread is attributed to `(no thread)`, was `<no thread>`.
- `jfrq-live growth` leaves out the GC's heap filler (`[Ljdk.internal.vm.FillerElement;`),
  which a quiet watch saw as its top grower, and says so.
- `jfrq-live`: each dump holds its read buffer in the target JVM for 400 minutes, a JDK
  behaviour ([LIVE.md](https://github.com/marregui/jfrq/blob/v0.2.0/docs/LIVE.md)). The
  buffer is now 128 KiB instead of 1 MiB, an eighth of the memory for about 20 ms more per
  dump.
