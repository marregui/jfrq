# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`jfrq`: a JDK 25 command-line tool that asks a JFR recording one question (`stalls`, `locks`, `alloc`, `health`, `info`) and answers it in text or a self-contained HTML report. `jfrq-live` asks the same questions of a running JVM by taking windowed dumps (`full`, `delta`, `again`) with a per-JVM cursor. Version 0.1.0, `group = dev.jfrq`. `README.md` is the front page and `docs/USAGE.md` the user-facing reference (every command, option and output rule), `docs/RECORDING.md` the recording settings; `docs/design/README.md` is the overall design (the read pass, output, damaged files, testing, performance, known limits) and points to `docs/design/<command>.md` (`stalls`, `locks`, `alloc`, `health`, `info`), which explain each detector, the JFR events it reads and the evidence hierarchy — read the command's file before changing a verdict or trusting an unexpected result; `docs/LIVE.md` explains the dump mechanics (clone-and-stop, whole-chunk windows, the `T + 1 ms` cursor rule, bounds) — read it before touching `live/`.

## Build and test

Gradle (Kotlin DSL), four modules, no convention plugins: each `*/build.gradle.kts` is self-contained on purpose. JDK 25 everywhere: the module toolchains, the Gradle daemon (`gradle/gradle-daemon-jvm.properties`, so the launching `java` may be older), the `.sdkmanrc` for the shell that runs the installed launcher. No toolchain auto-download: a local Temurin 25 must be installed. `core` has no runtime dependency beyond `jdk.jfr`.

```
./gradlew build                       # compile + tests + JaCoCo coverage gates (85 % core, 80 % cli and live) + doclint over all Javadoc + Checkstyle UnusedImports
java -cp core/build/libs/core-*-test-fixtures.jar ci/Smoke.java live   # after installDist: the launchers on a live JVM, as CI runs them (~50 s)
./gradlew installDist                 # live/build/install/jfrq/bin/{jfrq,jfrq-live} (one distribution, built by live/), netty-demo/build/install/netty-demo/bin/netty-demo
./gradlew :core:test                  # one module
./gradlew :core:test --tests 'dev.jfrq.core.stalls.StallAnalysisTest'
./gradlew :core:test --tests '*StallAnalysisTest.methodName'
```

- Compilation runs with `-Xlint:all -Werror`: any warning fails the build.
- `check` depends on `jacocoTestCoverageVerification`; dropping coverage below the module gate fails `build`.
- Configuration cache, parallel and build cache are on (`gradle.properties`).
- The version is in two places, `build.gradle.kts` and `Main.VERSION`; between releases it is the next one with `-SNAPSHOT`. A release: drop `-SNAPSHOT` in both, notes in `docs/releases/v<version>.md`, merged; then the tag `v<version>` on `master`, pushed. `.github/workflows/release.yml` builds, tests, smoke-tests, checks that the tag, the zip names and both `--version` lines agree, and opens a **draft** release with `jfrq-<version>.zip`, `netty-demo-<version>.zip`, `SHA256SUMS` and a provenance attestation per zip; it is published by hand.
- Tests in `core/.../jfr/RecordingTest`, `cli/.../MainTest` and the stall/lock tests make **real JFR recordings in-process** (`JfrFixtures.record`), so they take seconds and assert verdicts and orders of magnitude, not exact durations. Pure-logic tests (`StallAnalysisTest`, `ContentionReportTest`, `AllocationTest`) use hand-built timelines with exact expectations. `core/.../jfr/NativeThreads` makes a thread the JVM did not start (FFM `pthread_create` plus an upcall, POSIX only; the core tests run with `--enable-native-access=ALL-UNNAMED`), and `HealthCollectorTest` runs child JVMs for what the test JVM cannot record about itself (NMT, a squeezed heap). `live/.../LiveTest` **attaches to the test JVM itself** (`-Djdk.attach.allowAttachSelf=true` in `live/build.gradle.kts`) and runs the whole loop against a recording it starts there; the recorder is JVM-global, so every test names its recording and addresses it with `--recording`.

Run it after `installDist`:

```
netty-demo --scenario lock --duration 15s --out demo-lock.jfr
jfrq stalls demo-lock.jfr --thread 'event-loop-*' --timing
```

`--timing` prints parse/analyse/render phases to stderr; measure with it before and after any performance change (numbers in `docs/design/README.md` §5).

## Architecture

**One streaming pass, several sinks.** `core/jfr/JfrReader` opens the file with `jdk.jfr.consumer.EventStream`, subscribes only to the event types its `Sink`s declare (`Sink.eventTypes()`; empty set = everything, used by `info`), and dispatches each event. Three consequences every sink must respect:

1. `setReuse(true)`: the `RecordedEvent` is recycled between callbacks — copy what you keep, never retain the event.
2. `setOrdered(false)`: delivery is file order, not time order — sinks sort what they keep in `finish()`.
3. `RecordingInfo` depends on what was read, except where it cannot: `jdk.ActiveSetting` is subscribed on every pass, so settings/thresholds are the same on a filtered pass as on a full one, and the span comes from the chunk headers alone (`Chunks`), so every command reports the same span for a file. Event counts and the thread set cover only the event types the pass read (`info` reads everything).

`Sink` lifecycle: `begin(Interner)` → `accept(RecordedEvent, int kind)` × N → `finish(RecordingInfo)`. The `kind` is the `EventKinds` tag of the event type, resolved once per `EventType` object (by identity) rather than per event; collectors switch on it, and the one-argument `accept(RecordedEvent)` is the fallback for sinks that do not (tests). A `@Transient` parameter is one the callee does not retain.

**Per command:** a collector (sink) and a report.

| Command | Sink | Report / analysis |
|---|---|---|
| `alloc` | `alloc/AllocationCollector` | `AllocationReport`, `AllocationDiff` (`--baseline`, compares rates; both files parsed concurrently on virtual threads). Sites are ranked by a `SiteKey` — the culprit method, or the innermost frame in the packages `--app` names — and the diff folds both sides by the same key |
| `locks` | `locks/ContentionCollector` | `ContentionReport` (holder walk-back through `previousOwner`, convoy search; `--by-site` ranks one row per stack instead of per lock instance) |
| `stalls` | `stalls/StallCollector` | `StallAnalysis` + `IdleMatcher` + `Timeline` → `StallReport` |
| `health` | `health/HealthCollector` | `HealthReport`: findings the JVM reported (ranked by `Finding.Kind`, each with first/last time), the GC account, trends (floors of the first and last thirds, no verdict), throwables by class and by site (the site is below the throwable's own construction frames), the Java threads' CPU (`health/ThreadCpu`, each thread's first `jdk.ThreadCPULoad` reading left out) with a warning when the JVM's own `jdk.CPULoad` is below it or the JVM has JDK-8326446 (Apple silicon before 17.0.13, 21.0.4, 22.0.2, 23: figure at 3/125), NMT committed memory by category. JFR records an `OutOfMemoryError` only when Java code constructs it, never a JVM-made one or a `StackOverflowError`, and traces every other `Error` twice; see `docs/design/health.md`. Several recordings (`health a.jfr b.jfr`) are read concurrently (`Main.readAll`) into one comparison table (`HealthReport.comparedCells`) |
| `info` | everything, plus `report/ThreadCensus` | `RecordingInfo`; `RecordingSummary` folds threads into families with their life counts, `Attached` (a `jdk.ThreadStart` with no parent and no stack) and `CPU` (`ThreadCpu`); `--thread GLOB` adds `RecordingSummary.starts`: peaks per 100 ms and per second, creators by the innermost non-JDK frame. `docs/design/info.md` |
| `jfrq-live` (`live` module) | none: dumps a window from a running JVM over JMX, then delegates to `Main.run` | `Snapshot`, `Cursor`, the span check in `Live.check` |

**Model (`core/model`).** Timestamps are epoch nanoseconds in `long`; absence is `Nulls.LONG_NULL`, not `Optional` (the `Optional`/`Duration` accessors on `RecordingInfo` and `Stack` exist for reports and tests; per-event and analysis code uses `periodNanos`, `culpritOrNull`, `depth()`/`frameQuick(i)`). `Interval` is half-open `[start, end)`. `Interner` dedups `Stack`/`Frame`/`ThreadRef`/method names by identity of the JDK's constant-pool objects (a `RecordedObject` field lookup is a linear by-name scan, so every resolution is done once), and its value tables are probed with raw components (a frame's type/method/line/native bit, a stack's frame buffer) so a hit allocates nothing; the identity caches are bounded and cleared when full. `Stack` is a class with a cached hash, not a record, so aggregation maps compare by identity first. Sinks read event fields only through `core/jfr/Events`, naming them by `Fields` tag: whether a type has a field is a bit of a mask the interner resolves once per `EventType` object (`Interner.fields`), and a present value is read with one `getValue` scan (the typed getters scan twice). The two other readers: `JfrReader` reads `jdk.ActiveSetting`'s `id`/`name`/`value` directly, and `Interner.thread` picks the event's own thread field (`sampledThread` or `eventThread`) from that mask and reads it through `Events`.

**Collections (`core/coll`).** The per-event path runs on the project's own open-addressing tables and flat lists, not `java.util`: `ObjObjHashMap`, `IdentityObjObjHashMap`, `ObjLongHashMap`, `LongObjHashMap`, `ObjHashSet`, `ObjList`, `LongList`. They follow `CODING-GUIDELINES.md` §3: `keyIndex()` returns a negative index for a hit and the free slot for a miss, so get-or-insert is one probe (`int i = m.keyIndex(k); v = i < 0 ? m.valueAtQuick(i) : m.putAt(i, k, newValue())`); `getQuick`/`valueAtQuick` are assert-only; iteration is `for (s = 0; s < slots(); s++) if (hasKeyAtSlot(s))`; deletes backward-shift, never tombstone. Each table is a self-contained class (no shared base with virtual hooks: that made the probe loop megamorphic). `java.util` collections appear only in report objects (`AllocationReport`'s maps, `List`s on the records) and are built once in `finish()`. Keys read from the file can be any `long`, so `LongObjHashMap` keeps an entry whose key equals its no-entry key in a slot of its own. `HashTablesTest` cross-checks every table against `java.util` with a seed that every failure message names and `./gradlew :core:test -Djfrq.test.seed=<seed>` replays.

**Rendering.** Text (`cli/Text`, `core/util/TextTable`), HTML (`core/report/Html`) and JSON (`core/report/Json`, `--json`, which replaces the text on stdout) are all derived from the same report objects and bounded by the same `--top`; HTML is built behind a supplier only when `--html` is given. The JSON field names are a contract: `docs/JSON.md` lists them and `Json.SCHEMA` changes when one is renamed, removed or changes meaning. Tests read `--json` through the strict `JsonParser` in `core/src/testFixtures`. Every printed time is UTC and says so.

**CLI (`cli/Main`, `cli/Args`).** Hand-rolled parsing, no library. Exit codes: 0 ok, 1 recording unreadable, 2 usage error. `Main` holds the `USAGE` text; keep it in sync with `docs/USAGE.md` when an option changes. The launcher adds `-XX:+AutoCreateSharedArchive` so an AppCDS archive lands in `lib/jfrq.jsa` after the first run (`cli/build.gradle.kts` patches the start script for `$APP_HOME`). `Main.run(argv, out, err)` and `Args` are public because `live` reuses them.

**`live` (`live/Live`, `Jvm`, `Snapshot`, `Cursor`, `Window`).** `jfrq-live <pid> <command> [options] [-- <jfrq command>]`. `Jvm.attach` uses `com.sun.tools.attach` to start the target's local management agent and drives `jdk.management.jfr.FlightRecorderMXBean` over that JMX connector (it sets `java.rmi.server.hostname=127.0.0.1` on its own side: an unresolvable macOS hostname otherwise costs 5 s per connection). `Snapshot.take` is `jcmd JFR.dump` over JMX: `cloneRecording(id, stop=true)` seals the current chunk at instant `T`, `openStream` with `startTime`/`endTime` hands over every chunk overlapping the window (whole chunks, never cut), `closeRecording` on the clone. `Cursor` keeps `T + 1 ms` per JVM incarnation (`pid` + JVM start time) in `~/.jfrq/live/<pid>.properties`; the rule and why it makes deltas exact at chunk level is in `Cursor`'s javadoc and `docs/LIVE.md` §2. After each dump `Live.check` reads the file's chunk headers back with `Chunks.scan` and prints the span against the window; warnings when data was discarded by `max-age`/`max-size`, the recording started after the window began, or the recording is unbounded. A dump holds a lock (`<pid>.lock`) from loading the cursor to advancing it, and a shutdown hook closes the clone and deletes the `.part` file if the process is stopped mid-dump; the hook's JMX cleanup runs on a daemon thread bounded to 5 s (`Cleanup.HOOK_TIMEOUT`), and a JVM that does not answer in time gets the clone named on stderr with the `jfrq-live <pid> stop --recording <id>` command that closes it. The question after `--` is validated with `Main.check` before attaching. In-memory recordings (`disk=false`) have no chunks and fail with "holds no data in the window".

**`netty-demo`.** A Netty service with injected pathologies (`Scenario`, `RequestHandler`, `Background`), recorded in-process by `Recorder`; the walkthrough is `docs/TUTORIAL.md`. It is the only module with third-party dependencies.

## Coding rules for this repo

- The coding standard is the Java Coding Standard (`github.com/marregui/java-standard`, v2.0.1); cite rules by `G-<section>.<n>`. Read it and `CODING-GUIDELINES.md`, this repository's Apply section (the standard's 14 parts: version, hot paths, what was applied, departures, what is not applied, imports, doc comments, licence header, logging, tests, entry points, line limit), before writing code. Checkstyle runs the standard's configuration in `./gradlew check`. It was applied to the per-event path on 2026-09-18 and, for G-10.2 (`final` on every local, enhanced-`for` variable, catch parameter and method parameter that is never reassigned), to all four modules including tests on 2026-09-21 (see `CODING-GUIDELINES.md`); the report/rendering layer (`Text`, `Html`, the report records) is final reporting and stays on `java.util`, `String.format` and `Optional` by the guidelines' own exemption (G-2.3). A bare local or parameter now means "reassigned below": keep it that way when adding code.
- Per-event allocations that remain are the `Sample`/`Block`/`Wait` records and their `Interval`s (the analysis API and its tests are built on those records) and the `Instant` inside `RecordedEvent.getStartTime()`/`getEndTime()` (the only way the JDK exposes event timestamps). Everything else on the per-event path is a probe into a pre-allocated table: thread filter verdicts, lock and peer detail strings, idle verdicts per frame, event kinds and field presence per `EventType`.
- The standard, and anything derived from it here, must stay standalone: no references to the codebase it was distilled from, every example original.
- Anything a blocking event or pause explains is exact; anything resting on samples alone is bounded by the measured sampling cadence (`docs/design/stalls.md` §3). Do not add a sample-based verdict without the cadence check.
